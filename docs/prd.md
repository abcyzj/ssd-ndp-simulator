# SSD 近存计算仿真平台 V0.1 产品需求描述

版本：0.1  
日期：2026-10-22  
环境与依赖修订：2026-10-27，开发、构建与验收基线改为本机 macOS（Apple Silicon / arm64），MQSim 与 SST Core 已初始化为 submodule。  
用途：供 Codex 或其他编程工具开展架构设计、代码库调研、任务拆解与实施规划。  
状态：需求与规划输入；本文不表示任何组件已经实现或通过验证。

## 1. 产品目标与使用者

构建一个面向存储架构研究的、可编程的 SSD 近存计算仿真平台。第一版聚焦 ANNS，支持用户编写依赖真实计算结果的搜索逻辑，比较主机计算与 SSD 控制器侧计算的性能和数据搬运差异，并观察 SSD 内部不同粒度的行为。

主要使用者是负责负载分析、仿真评估与存储硬件需求研究的工程师。平台服务于架构评估，不以提出新 ANNS 算法、实现生产级向量数据库或保证近存方案加速为目标。

第一版应能回答：

- 相同数据、索引和搜索语义下，将指定算子放到 SSD 控制器侧，端到端延迟、吞吐和数据搬运量如何变化？
- 性能受 NAND 访问、通道并行、计算吞吐、缓冲容量还是主机与 SSD 之间的数据传输限制？
- 计算资源、缓冲资源和存储参数变化，如何影响搜索执行过程？
- 近存计算是否值得继续投入，以及哪些硬件参数最值得进一步细化建模？

## 2. 需求确定程度与第一版范围

本文使用以下标签，避免将尚未讨论的实现选择误当成既定需求：

- **确定约束**：当前方案已经收敛的目标与边界，规划时应保留。
- **建议默认**：为让 V0.1 可交付而提出的默认选择，可在规划中说明理由后调整。
- **待核实**：需要检查上游代码或实现条件后作出技术决策，不能假定已经具备。

### 2.2 第一版明确不包含

- 多 SSD、分布式检索、多主机协同。
- channel、die、plane 或 NAND latch 内部的计算放置；第一版的内部观测不等同于支持这些位置执行计算。
- 完整复现 REIS、NasZip 等具体硬件方案。
- 完整搜索控制流迁移至 SSD 自主执行。
- 索引在线增删改、并发写一致性、崩溃恢复、持久性验证。
- 完整操作系统、虚拟机、驱动栈或任意固件指令执行。
- 周期精确的加速器、RTL、复杂片上网络或精确电路级能耗模型。
- 同时接入 SimpleSSD、FEMU 等多个 SSD 后端。
- 必须依赖 NVIDIA GPU 或其他真实加速卡的功能执行。
- 生产级向量数据库、图形化控制台、用户权限系统。
- 全规模十亿级数据集和未经校准的硬件绝对性能承诺。

只读指应用层负载；不要求删除 MQSim 本身已有的初始化、映射或内部维护逻辑。初始设备状态和后台活动假设应被记录。

## 3. 关键用户流程

1. 用户准备向量、只读索引、查询及可选的精确近邻 ground truth。
2. 用户实现或选择算法插件，指定候选集更新、批次、停止条件和算子调用。
3. 用户选择主机计算或盘控侧计算，配置 SSD、计算、缓冲和传输参数。
4. 平台运行真实算法，根据返回结果动态生成后续操作。
5. 平台输出搜索结果、Recall、模拟性能、资源统计和可选事件轨迹。
6. 用户修改硬件参数或算子放置，重复实验并比较结果。

用户扩展算法和算子时，通常不应修改 MQSim 的 FTL、NAND 调度或 SST 事件内核。研究新的硬件位置或资源行为时，允许扩展后端适配和资源模型。

## 4. 架构职责

以下为逻辑职责划分，不强制每个职责对应一个进程、线程或 SST Component。

| 模块 | 输入与职责 | 输出 |
| --- | --- | --- |
| 算法前端 | 查询、算法参数、运行时返回值；执行循环、分支和候选集管理 | 动态产生的读取、计算、传输任务 |
| 闭环运行时 | 管理任务标识、输入句柄、依赖、放置、异步完成和恢复执行 | 有序的资源请求及在正确时间交付的结果 |
| 功能执行器 | 对真实数据执行距离、筛选、排序等语义 | 真实结果及工作量、输出规模描述 |
| 数据与布局管理 | 保存逻辑内容，管理对象到 LBA 的映射和模拟驻留状态 | 地址范围、数据句柄和位置/有效性信息 |
| MQSim 适配层 | 连接平台请求、后端事务、事件推进和内部观察点 | 存储完成事件、状态、统计 |
| 计算与数据传输模型 | 模拟主机/盘控计算、缓冲占用、队列、链路及相关竞争 | 资源事件、计算和传输完成事件 |
| 实验与观测模块 | 加载配置、采集统计、记录版本与假设 | 结果文件、事件日志、可复现实验记录 |

基本执行关系：

> 算法提交操作 → 运行时建立依赖 → 存储/传输使输入到达目标位置 → 功能执行产生数值 → 计算和返回路径完成 → 运行时交付结果 → 算法生成下一轮任务。

功能执行和性能建模独立实现，但由同一个任务标识、数据版本/句柄和模拟事件关联。结果交付由运行时统一控制。

## 5. 必须满足的功能需求

以下 FR 为 V0.1 必须满足的能力。建议默认项的具体实现可在规划中调整，但不能削弱这些能力。

### FR-01：结果驱动的动态算法执行

- 算法必须能读取真实距离、候选 ID 或其他算子结果，并据此决定后续访问。
- 支持循环、条件分支和依赖等待；不要求用户在运行前提供完整静态 DAG。
- 允许一轮内发起多个相互独立的操作。
- 不得以预先固定的完整访问序列替代闭环 ANNS 执行。
- trace 可以用于调试和对照，但不是第一版唯一的负载入口。

### FR-02：异步任务与结果可见性

- 读取、计算和传输操作返回异步句柄或等价机制。
- 数据句柄可以被传给后续任务；持有句柄不代表调用者可以立即读取其数值。
- 输入依赖满足且目标资源允许后，任务才能执行。
- 功能结果只能在对应模拟操作以及必要的返回传输完成后交付给消费者。
- 算法等待不得阻塞整个事件引擎，其他查询和独立任务应能继续推进。
- 依赖错误、无效句柄、无法容纳的请求和无法继续推进的状态应提供明确诊断。

不强制具体采用 future、回调、协程或状态机；规划中选择一种易与 SST 集成的机制。

### FR-03：功能执行与性能模型分离

- 算子功能实现必须产生真实结果，不能只返回占位值或随机距离。
- 算子性能由模拟资源和配置决定，不使用功能函数的实际墙钟耗时充当模拟耗时。
- 算子可提供处理元素数、计算次数、读写字节数和输出大小等工作量信息。
- 输出规模影响后续传输量；数据相关的计算量应反映到性能描述中。
- 若存在显著影响时序的内部提前退出或分阶段依赖，应拆分操作或明确建模，不能无条件套用固定总延迟。
- V0.1 建议先支持确定性、只读或纯函数形式的计算；不要引入未经设计的跨任务可变状态。

默认可在模拟输入就绪后执行功能函数，将结果暂存至模拟完成时再交付；无需为了第一版实现复杂的超前执行或回滚机制。

### FR-04：逻辑内容、地址与驻留位置分离

- 功能数据存储可使用仿真器所在机器的内存或文件。
- 平台应明确维护逻辑对象到 LBA/字节范围的映射，物理地址映射以 SSD 后端为准。
- 目标系统的数据驻留状态至少区分主机内存、SSD 侧缓冲和 SSD 存储。
- 即使功能执行器可以直接读取完整数据集，模拟任务仍必须经历其配置要求的存储和传输路径。
- SSD 侧缓冲应有容量、占用和释放规则；必要时形成等待或背压。
- 对跨页对象和读取粒度给出明确规则，区分逻辑有效字节与实际存储访问字节。
- 逻辑内容不能因 GC 等物理重定位而变化；研究观测到的 PPA 也不能被算法当成永久不变的地址。

### FR-05：统一时间与 MQSim 适配

- 统一的模拟时间语义由 SST 主导。
- 可以桥接 MQSim 内部队列，也可以改造其调度接口；具体方式由源码核查决定。
- 后端推进不得跨过可能影响其行为的外部事件；不得将后端独立跑到结束后再回填时延。
- 明确时间单位、转换方式和同一时间戳事件的稳定处理顺序。
- 保持平台任务与后端请求/内部事务的关联，处理好拆分请求和多个完成事件。
- 上层算法依赖平台接口，不直接访问 MQSim 全局对象或内部数据结构。
- 适配应作为需要开发和验证的工作，不能假设存在即插即用的 SST-MQSim 集成。

### FR-06：主机与盘控侧两种计算模式

两种模式使用相同的输入数据、索引、搜索参数和已声明的数值语义。

- **主机模式**：数据经模拟存储和主机接口路径到达主机后，由主机计算模型执行指定算子。
- **盘控模式**：将必要的查询/参数传至 SSD，在 SSD 侧读取数据并执行指定算子，再把主机决策需要的信息返回主机。
- 盘控模式不能在执行近存算子之前，默认将完整输入向量搬回主机。
- 若搜索控制留在主机，邻接表、候选 ID、距离及其他必要元数据的返回也必须计入。
- query、向量、邻接表、PQ 码（如使用）、候选状态分别位于何处，必须由具体算法配置或说明列明。
- 不要求所有算子都支持任意放置；不支持的组合应明确拒绝。
- 不以“盘控模式必须更快”作为成功标准。

默认示例采用确定的批次等待和候选排序规则，使数值语义不变时可以检查两种模式的功能一致性。若未来引入完成顺序驱动的搜索策略，应单独说明它对路径和 Recall 的影响。

### FR-07：资源计费、竞争与数据路径

- 存储由 MQSim 模拟；新增计算采用参数化模型。
- 至少描述计算服务时间、可服务任务数、等待队列和 SSD 侧缓冲容量。
- 主机与 SSD 间传输需计入实际使用路径的有效载荷、带宽和相关延迟。
- 主机候选集更新等控制工作采用明确的成本假设；不能将其真实程序耗时隐式计入模拟时间。
- 数据准备、计算、传输能否重叠，取决于依赖和资源，不应一律串行相加。
- SSD 内部的标准读取路径和近存读取路径必须区分；近存读取不能先承担一次无必要的完整主机返回，再执行设备内计算。
- 同一资源和一次访问必须只有一个权威计费位置，避免 MQSim 与外部模型重复统计延迟或流量。

规划阶段应给出资源归属表，至少覆盖 NAND、通道、MQSim 内部缓存/DRAM、近存计算单元、近存缓冲、主机 CPU 和主机接口传输。

第一版可以将新增近存缓冲建模为独立资源，但必须声明与 MQSim 内部缓存/DRAM 的关系。未实现共享 DRAM 竞争时，不得声称已经评估该竞争。

### FR-08：多粒度观测与算法可见信息

- 研究观测接口至少覆盖设备、请求、channel、die。
- 至少能导出请求提交/完成、实际可获得的通道或 die 活动/占用信息，以及由这些事件产生的统计。
- 所有观测带模拟时间和对应实体标识；事件日志应可按查询/任务关联。
- 只能暴露后端实际建模或通过已说明扩展得到的信息。
- 明确区分“研究者调试/统计接口”和“算法运行时可见接口”。
- V0.1 算法默认依赖结果与完成事件推进，不要求实现利用 SSD 全局内部状态的调度策略。
- 如允许算法读取内部状态，应声明目标架构的访问能力和获取成本，不能无成本使用研究者的全局观察视图。
- 不支持的粒度或字段返回明确的不支持状态，不能用零值伪装为真实结果。

### FR-09：可运行的 ANNS 示例

- 提供至少一个需要动态距离结果来更新候选集的端到端示例。
- 建议默认使用小型图 ANNS：显式入口、候选集、已访问集合、扩展批次和停止条件。
- 给出算法伪代码、数据格式、存储布局、计算放置和成本假设。
- 数据可由固定种子生成；必须包含真实向量和索引内容。
- 搜索结果包含 top-k ID 和对应距离；精确搜索可仅作为离线 ground truth 生成工具。
- 计算 Recall@k，并记录 k、搜索参数和 ground truth 定义。
- 不要求近似搜索的 Recall 恒为 1；不能把功能模型自算的近似结果直接当成准确率真值。

在简化示例之外，预留接入 DiskANN/AISAQ 等真实实现的边界，但不要求第一版完整移植它们。

### FR-10：实验配置、结果和复现

- 提供最小可运行配置和两种计算模式的示例配置。
- 支持单查询及有限并发查询，明确提交方式和并发上限；无需第一版实现复杂负载生成系统。
- 将运行参数与代码解耦，至少覆盖算法参数、算子放置、SSD 参数、计算能力、缓冲容量和传输参数。
- 输出机器可读的配置快照、结果及统计；JSON/CSV 等格式由规划选择。
- 记录数据集/索引标识、随机种子、代码与依赖版本、预热或设备初始状态、模型假设。
- 事件日志可关闭，避免大规模日志成为默认运行负担。
- 相同输入、版本和配置应具备可复现结果；不要求跨平台比特级浮点一致，但应定义合理的数值容差和同分排序规则。

## 6. 最小结果集与评价口径

| 类别 | 最低输出要求 |
| --- | --- |
| 搜索正确性 | top-k ID、距离、Recall@k、查询和算法参数 |
| 查询性能 | 每查询模拟延迟、查询数量、吞吐；多查询时给出分位数及样本数 |
| 存储行为 | 主机/设备内部请求数量与字节量；能够关联到查询的访问事件 |
| 数据搬运 | 主机到 SSD、SSD 到主机的字节量；明确逻辑有效量与链路实际模拟量 |
| 计算行为 | 任务数量、工作量、服务时间、排队等待 |
| 缓冲行为 | 容量、峰值占用、等待或背压情况 |
| SSD 内部 | 实际支持的 channel/die 活动与忙闲/利用率统计，并说明定义 |
| 仿真效率 | 实际墙钟运行时间；有条件时报告内存占用，与模拟性能分开 |
| 可复现性 | 配置、数据标识、依赖版本、初始状态与假设 |

存在重叠执行时，各模块累计忙时和等待时间不能直接相加作为端到端延迟。延迟拆解应说明统计口径，必要时以事件轨迹解释关键依赖链。

第一版以相对比较、因果正确性和模型透明性为目标。参数来源可为公开资料、人工设定或后续测量，但必须标注来源；未经实测校准，不能宣称绝对硬件性能预测已经准确。

## 7. 验收标准

以下验收必须有可重复的输入、配置和预期行为。规划应将其落实为有意义的测试或实验，不要求机械地为每个辅助函数增加测试。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 最小端到端运行 | 一条明确的命令可运行小数据集，输出 top-k、距离、Recall、模拟延迟和配置记录；可运行两种计算模式 |
| AC-02 | 结果改变访问路径 | 构造无同分歧义的案例，只改变会影响排序的向量内容，观察到预期的下一轮候选或 LBA 访问变化 |
| AC-03 | 延迟影响后继任务 | 在无其他瓶颈的受控依赖链中增大读取/计算/返回延迟，后继任务不得提前，且按预期推迟；独立任务不被全局阻塞 |
| AC-04 | 结果不能提前可见 | 即使功能结果已经算出，依赖方也不能在模拟计算与必要传输完成前读取结果或发起依赖该结果的决策 |
| AC-05 | 两种放置功能一致 | 默认确定性策略下，相同输入和数值语义产生一致的 top-k、候选决策及容差内距离；两种模式的模拟数据路径可不同 |
| AC-06 | 近存数据路径正确 | 盘控模式无多余的完整向量主机往返；同时正确计入 query 输入和主机需要的邻接信息、ID、得分等输出 |
| AC-07 | 容量与竞争有效 | 缓冲不足时出现等待或背压，峰值占用不超容量；构造共享资源任务时观察到符合模型的排队 |
| AC-08 | 存储适配保持基线 | 关闭近存功能，以相同配置、初始状态和受控 I/O 对照 MQSim 原生运行，确认请求完成行为一致，或解释并验证允许的时间量化差异 |
| AC-09 | 观测能力可信 | channel/die 事件带时间与实体标识，统计可由事件核对；不存在的 plane/latch 能力明确标记为不支持 |
| AC-10 | 运行可复现 | 相同种子和配置重跑结果稳定；修改功能执行实现的真实运行速度不会直接改变模拟硬件耗时 |
| AC-11 | 参数具有正确影响 | 在刻意隔离瓶颈的实验中，计算服务率、链路带宽等参数改变对应行为；不要求任意复杂负载下结果均呈简单单调趋势 |

AC-08 的输入可使用专门的 I/O 微基准；它不替代 AC-02 所需的 ANNS 闭环验证。

## 8. 交付物与建议里程碑

交付物至少包含：

- 主机模式与盘控模式配置。

- 对应第 7 节的验证记录。
- 已实现能力、模型简化、未校准参数和已知限制的说明。
- 上游代码改动清单及其维护方式；保持许可证信息。

建议按以下依赖推进，具体目录结构和工作量由规划输出：

| 里程碑 | 可评审结果 | 对应验证 |
| --- | --- | --- |
| M0：上游核查与设计 | 版本锁定、事件适配方案、资源归属表、能力矩阵、最小数据流 | 明确 MQSim 集成风险与所需改动 |
| M1：单 SSD 存储闭环 | SST 能提交访问并接收 MQSim 完成事件，支持最小观测 | AC-08、AC-09 的基础部分 |

## 9. 规划阶段必须解决的问题

这些问题应先给出证据、选项和推荐，不应直接转化为无限扩展的开发范围。

1. **事件引擎如何接入？** 核实所选 MQSim 版本的时间推进、事件注册、全局/静态状态与初始化过程。选择可维护的桥接方式，说明同刻事件顺序和外部事件插入规则。
2. **近存路径截取在哪里？** 确认数据在盘控侧可用的事件位置，以及怎样避免沿完整主机读取路径计费；缓冲和资源何时释放。
3. **哪些资源归谁管理？** 明确后端内存/缓存、额外近存缓冲、传输链路和计算单元的边界，避免重复计费或遗漏竞争。
4. **首个算法如何落地？** 比较简化图搜索与复用已有 DiskANN 代码的工作量，推荐最小可验收方案并注明语义差异。
5. **观测点能支持哪些指标？** 列出原生可获得、需少量扩展、第一版不支持的字段；不能从接口名称推断模型精度。
6. **语言、接口和构建如何选？** 优先兼容现有 C++ 仿真生态；是否增加 Python 前端是可选决策，不要默认引入跨语言绑定。
7. **默认参数如何解释？** 给出参数单位、来源和适用范围；未知参数允许配置，但不能伪造已校准值。
8. **最小实验的规模与成本如何定？** 根据可用 CPU/内存与实际运行测量确定，不预设依赖专用加速卡，也不填写未经验证的吞吐指标。

应优先消除事件适配和近存数据路径两项风险，再扩大算法与实验规模。

## 10. 后续演进边界

第一版只保留必要的职责边界，不要求实现通用插件市场或复杂扩展框架。

| 后续方向 | 第一版应保留的边界 | 第一版不需要完成 |
| --- | --- | --- |
| channel/die/plane 侧计算 | 算子放置与存储适配分离，资源位置显式描述 | 这些位置的执行器、latch 模型或 REIS 数据通路 |
| SSD 自主搜索 | 算法逻辑不直接依赖主机墙钟或 MQSim 全局变量，消费者位置明确 | 设备内部完整搜索控制、跨位置控制迁移 |
| PQ、IVF、过滤等 | 功能算子与成本模型可分别注册 | 所有算法实现与优化 |
| Embedding pooling 等其他负载 | 通用操作、数据句柄和依赖机制 | 新负载的完整端到端示例 |
| 更精细计算/内存模型 | 工作量描述与资源服务模型分离 | 周期精确建模、完整共享 DRAM 竞争 |
| 多 SSD 或其他后端 | 不把算法写死在单一后端内部类型上 | 多实例状态隔离、分布式同步、多后端兼容层 |
| 可写负载 | 内容、位置、可见性职责明确 | 版本一致性、故障恢复与持久性语义 |

## 11. 给 Codex / 编程工具的规划任务

请基于本文件开展规划，当前任务是产出可执行的实施方案，不是立即实现所有模块。

规划输出应包含：

1. 对目标、V0.1 范围和非目标的简要复述，指出存在冲突的地方。
2. 对 SST 和 MQSim 所选版本的实际源码核查；列出相关入口和需改动位置，不编造已存在的集成接口。
3. 总体架构与模块职责，说明真实数据、数据句柄、任务和模拟事件如何关联。
4. 一轮 ANNS 的具体数据流与时序，分别覆盖主机模式和盘控模式；列明 query、向量、邻接信息和得分的路径。
5. 关键接口草案与资源归属表，保持到足以拆解开发任务的粒度，不急于设计全部类。
6. 按 M0–M4 拆分任务，给出依赖、可评审交付物和映射到 AC 编号的验收方法。
7. 主要风险、可降低风险的先行实验，以及建议默认和待核实项的推荐决定。
8. 建议目录结构、构建与运行方式、依赖版本管理方案。
9. 工作量按模块给出相对大小或有假设支撑的区间，明确不确定性，不给出无依据的精确工时。

规划约束：

- 保持单 SSD、只读 ANNS、盘控侧计算的第一版边界。

- 不因接口可扩展就提前实现后续全部硬件位置和算法。
- 对不影响目标的常规实现选择给出推荐并继续规划；仅将真正改变范围或模型结论的问题列为需确认事项。
