# M1.1 库化与生命周期骨架

2026-10-27（Asia/Shanghai）。M0.2 依赖已满足，M1.1 按限定范围验收通过；没有开始 M0.3a。首次运行证据见 [索引](evidence/m1.1/README.md) 和 [历史 manifest](evidence/m1.1/acceptance-2/manifest.json)；按用户要求直接修改 MQSim 子模块后的组织方式见 [源码维护约定](mqsim-source-management.md)，复验记录见 [direct-source manifest](evidence/m1.1/direct-source/manifest.json)。

## 实现及边界

[CMake 入口](../CMakeLists.txt) 默认通过 一个 [Python 准备脚本](../tools/prepare_sst.py) 在配置阶段准备并构建锁定的 SST，并安装到仓库固定的 `.cache/sst/<配置键>/install`，供相同配置的不同构建目录共享；无须先运行 M0.2 脚本。显式指定 SST_ROOT 时才导入已有 SST 配置。两种模式都通过 `SST::SSTCore` 提供头文件，并按 Darwin module 规则解析核心符号。`mqsim_pic` 直接编译 `third_party/MQSim/src`，不导出或打补丁；它是排除 `main.cpp` 的 C++17 PIC 静态库，链接进 `libndpsim.so`；macOS 上该元素文件使用 CMake MODULE 的 `.so` 后缀，不假设它必须是 `.dylib`。库目标不使用原生析构符号别名选项。

[LifecycleBackend](../src/backend/lifecycle.cc) 在 Reset 后构建一个真实 `SSD_Device`，并创建一个不产生请求的地址/资源分区参数。没有构建 `Host_System`、PCIe 端点或应用 flow；没有读取 workload/trace。`initialize()` 调用抽出的 MQSim 初始化阶段：连接触发器、校验对象、执行启动钩子，保留原生 unordered_map 顺序；不进入事件循环。映射启动钩子仍执行原生初始化元数据操作，这不等于 M1.3 的数据预装载。

[ndpsim.System](../src/sst/system.cc) 运行 SST init/setup/finish，通过一个 1 ns SelfLink 事件释放 primary 存活约束。正常输出为 `finish SST=1 ns MQSim=0 ns; device destroyed`；该 1 ns 是骨架调度探针，不是 SSD 服务延迟。finish 幂等，清空引擎的非 owning 注册表后析构设备；提前析构也会清理。生命周期状态错误及同进程第二次设备构建明确拒绝。曾在开发中重复调用 MQSim Reset 导致 use-after-free，最终实现避免 finish 后再 Reset；不据此承诺上游 Reset 可任意重复。

本轮只开放 `device_count=1`、`profile=native-small`，未知参数、零/多设备、非法数字、未知 profile、多个组件及多线程均失败退出。`native-small` 将现有 [原生小设备配置](../configs/native/ssdconfig.xml) 编入库，使用 2 channel × 1 chip × 2 die × 1 plane、64 block × 64 page、4096 B page、SIMPLE/TURNED_OFF 数据缓存、保留 CMT；不开放任意 XML 配置入口。所有延迟/带宽等参数仍为 **configured_unvalidated**。这一有界 profile 仅用于生命周期，不表示其他几何、缓存或 Host/I/O 生命周期已支持。

MQSim 基类虚析构、非交互错误和小型释放修复现直接保存在 `third_party/MQSim`，九个改动文件及全部受 Git 管理的文件与先前构建副本逐字节一致，见 [迁移核对](evidence/m1.1/direct-source-migration.json)。已删除 patch/series 及构建时源码准备工具；源码 HEAD、相对原生基线的 diff 哈希和逐文件哈希由验证入口记录。SST Core、原生 oracle 源码/二进制及 `deps.lock.json` 未修改；MQSim 改动尚未提交或推送，gitlink 未更新。后续提交方式见 [维护约定](mqsim-source-management.md)。

## 实际运行及复现

当前常规构建只需 `cmake -S . -B build`、`cmake --build build -j2`，随后 `ctest --test-dir build --output-on-failure` 或 `cmake --build build --target run_lifecycle`。所需工具与参数见 [README](../README.md)。下方完整回归脚本额外依赖已有原生 oracle 回执，用于历史对照，属于可选验证工具；平台构建不依赖它。 单 Python 脚本准备 SST 的首次构建、六项 CTest、重复配置、安装修复与配置变更检查已通过，见 [当前构建流程证据](evidence/python-sst/README.md)；[先前 ExternalProject 流程](evidence/cmake-build/README.md) 仅保留为历史。

完整回归入口（锁定的 Python、编译器、SDK 与原生 oracle 沿用 M0.2；平台所用 SST 默认由 CMake 重新构建，也可通过 --sst-root 显式复用；选择不存在的 build/output 目录）：

```sh
/opt/homebrew/Caskroom/miniconda/base/bin/python3.13 tools/verify_m1_1.py \
  --build-root build/m1.1-repeat --output results/m1.1-repeat
```

首次验收使用默认 `build/m1.1-acceptance`，输出 `docs/evidence/m1.1/acceptance-2`；直接源码复验使用 `--build-root build/m1.1-direct-source --output docs/evidence/m1.1/direct-source`。复现工具无下载、自动升级、Git 初始化或远端写入。manifest 保存主仓 commit、未提交输入源码哈希、MQSim 工作区身份与文件哈希、原生回执与二进制哈希、每条 argv/cwd/环境、退出码、日志 SHA256、墙钟秒数及断言。墙钟只说明仿真器开销。

也可直接运行已有构建：

```sh
build/native-macos/install/sst/bin/sst-info \
  --add-lib-path=build/m1.1-direct-source ndpsim.System
build/native-macos/install/sst/bin/sst \
  --add-lib-path=build/m1.1-direct-source configs/m1.1/lifecycle.py
/opt/homebrew/bin/ctest --test-dir build/m1.1-direct-source --output-on-failure
```

## 已知限制与失败记录

- 无后端事件推进、外部 I/O、本地读取、ANNS、资源服务模型或性能测量；E1/E2、AC-01～AC-11 均未运行，不宣称 AC-08 时序等价。单进程、单 rank、单线程、一个设备生命周期；每次实验新进程。
- AddressSanitizer 只覆盖本轮支持的无 I/O 图和异常探针，不证明全部上游对象、在途事务、构造中途内存耗尽或共享 CMT 多 flow 清理已安全。MQSim 仍有未审计的长期分配和静态实例，未做完整泄漏验证。
- 开发时额外 UBSan 检查在 `CMRRandomGenerator.h` 的 `mm_mul`/`mv_mul` 检出有符号乘法溢出。原始诊断保留在 [开发记录](evidence/m1.1/development/README.md)；未修改随机数算法以免改变后续存储基线，未声称 UBSan 通过。正式生命周期验收中的 ASan 未包含 UBSan。
- 初次尝试整套旧 M0.2 验证器因沙箱禁止 `/usr/bin/time -l` 查询 `kern.clockrate` 失败，见 [失败 manifest](evidence/m1.1/acceptance-1/manifest.json)。最终验收直接核对旧回执、工具/Python/所有二进制哈希，并复跑原生小读；没有重新采集 RSS 或重建 SST，不覆盖旧失败日志。
- 编译仍有上游未使用表达式/非完整返回路径等警告，见构建日志；未以消除全部上游警告扩大本轮范围。
